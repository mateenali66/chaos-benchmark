# Pre-Registered Statistical Analysis Plan

Registered before any data collection for the revised study. The commit introducing this file predates the first experimental run of the revision campaign; the manuscript will cite this commit hash as the pre-registration record. No analysis decision below may be changed after data collection begins; any deviation must be disclosed in the manuscript with rationale.

## Study components

### Component 1: Tool benchmark (RQ2)

- Design: 12 fault scenarios x 2 tools (Chaos Mesh 2.8.x, LitmusChaos 3.x) x **n = 30 repetitions** per cell = 720 runs.
- Infrastructure: two identical EKS clusters (ca-central-1, 3x m5.xlarge, ON_DEMAND, single instance type), runs strictly serial within a cluster. Identical AMI, Kubernetes version, and DeathStarBench deployment on both.
- **AMENDMENT 2026-08-15 (before any Component 1 data collection; overhead-stage pilot data motivated both changes):**
  1. **Crossover allocation replaces one-tool-per-cluster.** Component 2 stage (a) pilot baselines revealed material inter-cluster variance between the identically provisioned clusters (mean throughput 44.1 vs 71.6 rps), so a one-tool-per-cluster split would confound cluster with tool. Amended allocation: each cluster runs BOTH tools in counterbalanced order (bench-a: Chaos Mesh reps 1-15 then LitmusChaos reps 16-30; bench-b: LitmusChaos reps 1-15 then Chaos Mesh reps 16-30). Each tool still accrues n = 30 per scenario, 15 per cluster; the tool contrast is estimable within cluster and the confirmatory analysis is unchanged. Cluster is recorded per run and a per-cluster stratified view is reported as a robustness check.
  2. **Application resource envelope raised.** The DeathStarBench chart's default global resources (100m CPU / 128Mi memory, requests = limits, all 27 services) OOMKill stateful pods under the study load and CPU-throttle every service, producing pilot baseline error rates of 0-29% across runs. All Component 1/2/3 data collection uses the override in `helm/dsb-values.yaml` (requests 100m/256Mi; limits 1000m/512Mi; the CPU limit was raised from an interim 500m after per-run telemetry showed the single-threaded redis pods pinned at the 500m cap, whose CPU throttling alone produced seconds-scale p99 tails). Protocol acceptance pilot under the final envelope: two fully reset+warmed repetitions at 120 rps agreed within 0.1% on throughput (119.58 vs 119.68 rps) with p99 89 vs 95 ms and zero errors. Overhead-stage pilot data collected under the starved spec is archived under `overhead-tainted-128Mi/` and excluded from analysis; Component 2 is re-collected in full under the amended spec.
  3. **Per-repetition state reset added to the protocol (2026-08-15, before any Component 1 data).** Re-collected overhead pilot data under the amended resource envelope revealed monotonic cross-repetition degradation: with no cleanup between runs, accumulated writes (~24k posts per 300 s window; 88,662 documents after one stage) progressively slowed the application from 160 rps / 1.5% errors (fresh) to 11 rps / 74% errors (rep 10). Repetitions are only exchangeable from identical initial state, so every Component 1/2/3 repetition is now preceded by a full application-state reset (stateful pods recreated, social graph re-initialized, timeline read verified; `scripts/reset-app-state.sh`, ~215 s). Overhead data collected without resets is archived alongside the 128Mi-tainted data and excluded. This phenomenon is itself reported in the paper as a repetition-validity finding for chaos benchmarks.
  5. **Sidecar pre-window buffer fixed to eliminate warmup overlap (2026-08-16, after Component 1 completed; applies going forward, not retroactive).** Independent audit + manual re-derivation from real run timestamps found the sidecar's nominal 60s pre-baseline buffer (`window_start = baseline_start - 60`) structurally overlapped roughly the first 40 of those 60 seconds with the excluded warmup job's own traffic (warmup traffic ends only ~15-20s before `baseline_start`, not >=60s as the fixed offset assumed). Affects only the sidecar's exploratory pre-window telemetry, never the primary/secondary confirmatory metrics (wrk2 output, the officially recorded baseline/fault/recovery phases) or Component 1's statistical conclusions, which are unaffected and remain final. Fixed in `chaoslib.run_warmup`, which now returns its true completion timestamp, threaded into `window_start` in place of the fixed offset; the pre-window is therefore variably shorter (~15-20s of genuinely clean context) rather than a fixed 60s with contamination. Component 1's 720 already-collected sidecars retain the old, disclosed overlap and are NOT re-collected; the fix governs Component 3 (campaigns, not yet started) and any future re-run.
  4. **Offered load reduced to 120 rps and a 120 s excluded warm-up added (2026-08-15, before any Component 1 data).** Pilot runs (with the latency parser corrected to read wrk2's minute-suffixed values, which the original study's tooling silently recorded as 0) showed the original 200 rps offered load saturates the SUT: fresh-state capacity is ~160-180 rps, so corrected p99 latencies reached the minute scale even on clean baselines and latency measured queueing collapse rather than fault impact. The campaign offers 120 rps (~2/3 of measured fresh-state capacity), and each repetition begins with a 120 s warm-up window under load that is excluded from all measurements (post-reset cold caches and pools otherwise dominate the tail). Both values are fixed for every run of every component (`CHAOS_LOAD_RPS`, `CHAOS_WARMUP_S`).
  6. **Component 4 ground-truth source clarified; Component 3 arm count corrected from three to five (2026-08-16, before Component 3 campaigns or any Component 4 scoring).** Two drafting gaps caught while building the Component 4 scoring script: (a) "Ground truth: Component 1 benchmark medians and weakness signals" (Component 4, below) is only literally true for the 12 of 36 fault-space candidates whose (scenario_template, target_service) pair matches one of Component 1's original 12 scenarios (`experiments/scenarios.yaml`) -- fault-space.yaml deliberately expands each template to 3 target services (`experiments/fault-space.yaml`'s header), so the other 24 candidates have no Component 1 run to ground-truth against. Amended rule, applied uniformly and mechanically (no candidate-by-candidate discretion): for each of the 36 candidates, ground truth is the median/weakness-signal outcome from every REAL fault-window execution of that exact (scenario_template, target_service) pair across Component 1's 720 runs AND Component 3's 500 campaign injections (both use the identical `chaoslib.run_fault_protocol` execution path and weakness-signal thresholds, so pooling is methodologically sound), pooled without preference for either source. A candidate is only scored in Component 4 once at least one real execution of it exists; candidates with zero real executions after Component 3 completes are reported as excluded from scoring, not imputed. (b) The Confirmatory analyses' Kruskal-Wallis test (#5, below) said "across the three strategies"; Component 3's design (this file, above) and `../jss/ML_ARM_DESIGN.md` have specified five arms (random, coverage, and three distinct LLM models) since the design was frozen. Corrected to "five arms" for consistency; the test itself (Kruskal-Wallis across arms, Holm-corrected pairwise Mann-Whitney U on rejection) is unchanged. (c) Ground-truth threshold for prediction (i) (throughput_direction) fixed, since neither the original text nor Component 4's schema specified one: both Component 1 and Component 3 record throughput as a SINGLE wrk2 job spanning the whole baseline+fault+recovery[+cooldown] protocol window (`compute_weakness_signals`'s docstring already discloses this same single-wrk2-job limitation for the recovery/p99 signals), not a fault-phase-isolated figure, so ground truth for a candidate is that run's aggregate `throughput_rps` compared against the pure no-fault steady-state baseline (Component 2's `aggregate_throughput_rps` = 119.7 rps, `experiments/component4-baseline-summary.json`). Rule: `degrade` if `(119.7 - run_throughput_rps) / 119.7 > 0.10` (a 10% relative drop), else `no_meaningful_change`. 10% is chosen because the protocol-acceptance pilot above (Component 1, amendment item 2) already established baseline-to-baseline noise of ~0.1% (119.58 vs 119.68 rps across two clean repeated runs), so 10% sits two orders of magnitude above measurement noise while still catching every fault family this study's practitioner-heuristic baseline (`scripts/practitioner_heuristic.py`) predicts as degrading. When multiple real runs exist for one candidate (pooled per (b) above), the candidate's ground-truth throughput_rps is their median.
  7. **Component 4 ground-truth source corrected to Component 3 only; item 6's stated overlap count and CI method fixed; timing gap disclosed (2026-08-18, after Component 3 completed and Component 4's mechanical scoring first ran, before any results are used in the manuscript).** An independent three-review audit of the first real Component 4 scoring run (36/36 candidates, all real data) caught three problems in item 6 above, none changing its underlying intent but all needing correction before this document can be cited as an honest methods-section record: (a) item 6a's stated overlap count is wrong -- it says "12 of 36" candidates share a (scenario_template, target_service) pair with one of Component 1's original 12 scenarios; the true count, checked directly against `experiments/fault-space.yaml` and `experiments/scenarios.yaml`, is **3 of 36** (C01/pod-kill/compose-post-service, C14/latency-100ms/post-storage-service, C16/latency-300ms/user-timeline-service). Any manuscript text must say "3 of 36," not "12 of 36." (b) Item 6a's pooling rationale ("both use the identical execution path, so pooling is methodologically sound") did not disclose that Component 1's protocol window (baseline 300s + fault 120s + recovery 60s + cooldown 60s = 540s, fault = 22% of window) differs from Component 3's (baseline 120s + fault 120s + recovery 60s + no cooldown = 300s, fault = 40% of window) -- this file's own Component 1 protocol line, above, vs. Component 3's `chaoslib.CAMPAIGN_*_DURATION` constants. This is not hypothetical for the 3 overlapping candidates: C14 (latency-100ms, post-storage-service) classifies `no_meaningful_change` from Component 1's 60 runs alone (median 119.8 rps) but `degrade` from Component 3's 4 injections alone (median 24.69 rps, a 79% drop) -- pooling numerically drowns Component 3's real, protocol-matched signal under Component 1's 15x larger n and reports `no_meaningful_change`, the wrong answer by Component 3's own fresher evidence. AMENDED RULE: Component 4's ground truth is now sourced from Component 3's 500 campaign injections ONLY (`data-v2/ml/campaigns/*/campaign-*/injection-*.json`, matched by `candidate_id`); Component 1 is no longer pooled in. This costs no coverage -- Component 3 alone provides at least one real execution for all 36/36 candidates, verified directly (min 1, max 38 injections per candidate) -- and removes the confound entirely rather than attempting to correct for it. `component1_runs_for()` remains in the codebase for any future appendix-level robustness check but is not used for the primary Component 4 ground truth. (c) Item 6's text never specified a bootstrap CI method or resample count for Component 4 (only Confirmatory analysis #3, a Component 1 effect-size CI, registers BCa with 10,000 resamples); the scoring script's docstring incorrectly implied continuity with that convention ("matching Component 1's convention"), which was never actually registered for Component 4. AMENDED, registered explicitly now: Component 4's 95% CIs use a plain percentile bootstrap, 10,000 resamples, fixed seed 42, computed once per arm over that arm's scored (prediction, ground_truth) pairs. (d) Disclosed timing: Component 4's 540 raw hypothesis-generation samples were collected 2026-08-16 18:11-19:00 UTC, roughly 1.5-2 hours before item 6c's degrade-threshold rule was finalized (commit `1b0eae0`, 20:28 UTC the same day) -- the rule was written to fill a gap the scoring script exposed, not decided independently of the code that would apply it. Git history shows no intermediate step of inspecting individual predictions before the rule was written, and the rule itself is a mechanical, uniform formula with no candidate-specific discretion, but the manuscript must state this timing plainly rather than let item 6's own header ("before Component 3 campaigns or any Component 4 scoring") imply a cleaner separation from Component 4 data than existed. (e) Added: alongside chance (0.5) and the practitioner heuristic, Component 4 now also reports a trivial "always predict the majority ground-truth class" baseline and each arm's raw predicted-label distribution, so a constant/degenerate predictor (an arm predicting the same label for every candidate, which mechanically produces exactly 0.5 balanced accuracy with zero bootstrap CI width) is visible in the printed output rather than requiring inspection of the raw JSON to discover, and so any baseline's apparent edge over chance can be checked against the trivial-baseline floor before being described as evidence of calibrated judgment.
- Protocol per run: state reset, then 120 s excluded warm-up, then baseline 300 s under wrk2 load at 120 rps, fault 120 s, recovery 60 s, cooldown 60 s.

### Component 2: Overhead decomposition

- Three configurations x 10 repetitions per tool cluster: (a) no chaos tool installed, load only; (b) tool installed and idle, load only; (c) tool + fault (drawn from Component 1 data).
- Purpose: separate standing agent overhead (b minus a) from fault side effects (c minus b). Descriptive analysis with bootstrap CIs; no hypothesis test is registered for this component.

### Component 3: Fault-selection strategy study (RQ3)

- Design: 5 arms (random, coverage heuristic, and three LLM agents backed by distinct Bedrock models) x **10 campaigns** per arm; each campaign selects and executes K = 10 injections from a fixed 36-candidate fault space on the dedicated third cluster. The LLM agents select from pre-registered experiments via the LitmusChaos MCP server tool set (select-and-launch granularity; the MCP server exposes no experiment-composition tool, and the paper claims selection, not authoring).
- Random strategy is seeded (seeds 1-10, recorded). LLM arms: model IDs, prompt template, temperature, and tool configuration are frozen in the repo before campaign runs begin.

### Component 4: LLM hypothesis generation study (new RQ, taxonomy-gap phase)

- Design: for each of the 36 fault-space candidates, each of the three LLMs (same frozen models as Component 3), given only system topology and steady-state baseline telemetry (no fault data), predicts before injection: (i) direction of throughput impact (degrade / no meaningful change), (ii) which services' p99 latency degrades beyond 3x baseline, (iii) whether the weakness-signal set will be non-empty. 5 sampled generations per model per candidate (fixed seeds/temperature).
- Ground truth: real fault-window medians and weakness signals from Component 3's 500 campaign injections only, matched by `candidate_id`, for each of the 36 fault-space candidates -- see amendment item 7 below for why Component 1 pooling was dropped (a demonstrated, not merely theoretical, confound), and item 6 above for the exclusion-not-imputation rule for any candidate with zero real executions. Baselines: a practitioner-heuristic prediction (rules written and frozen before data collection), chance, and a trivial always-predict-the-majority-class baseline (item 7e).
- Primary metric: balanced accuracy of prediction (i) against ground truth, per model, with 95% percentile bootstrap CIs (10,000 resamples, seed 42 -- item 7c). Secondary: precision/recall of the service-set prediction (ii), calibration of (iii). Comparisons across models and against baselines are descriptive with CIs; no significance test is registered (36 candidates give limited power and candidates are not independent).
- No cluster time is consumed; this component runs after Component 1 data exists and is scored mechanically.

### Component 5: ML impact detection study (analysis-phase evaluation)

- Design: anomaly detectors trained per run on baseline-window telemetry and evaluated on the full run timeseries; task = flag the fault window. Labels = recorded injection start/end timestamps. Detectors (frozen list): EWMA control chart, Isolation Forest, reconstruction autoencoder, Deep SVDD. Baseline comparator: the static SLO threshold rules defined in Component 3's weakness signals -- amended, see below.
- Data: the per-run raw Prometheus timeseries sidecars from all Component 1 runs (720 runs). Train/evaluate split is per-run (train on that run's baseline, score the whole run); no cross-run learning, so there is no leakage channel from test faults into training.
- **Primary metric: AUC-ROC** over window-level scores, reported per detector with 95% bootstrap CIs across runs. F1 is reported only as a secondary, threshold-dependent metric and never compared across differently-prevalent subsets. Confirmatory comparison: each ML detector vs the static-threshold baseline on AUC-ROC, Wilcoxon signed-rank paired per run across the 720 runs, Holm correction across the 4 detectors.
- **AMENDMENT 2026-08-18 (before any Component 5 code was written; discovered while building the feature-extraction/detector pipeline, before any detector saw real data):**
  1. **HTTP-level telemetry is unusable; features are infrastructure-level only.** The sidecar's own recorded query metadata defines `http_request_rate`, `http_error_rate`, and `http_latency_bucket` (Envoy-based), but all three return ZERO Prometheus result series in every Component 1 run checked (verified across a 15-run sample spanning both tools and multiple scenarios, then confirmed at scale: 0/719 runs had any HTTP-metric data) -- Envoy sidecars were evidently never deployed/scraped in this cluster, despite the query being defined and recorded. Detector features are therefore the 7 genuinely populated series: container CPU usage, container memory working set, container network rx/tx bytes, pod restarts, node CPU utilization, node memory used (aggregated across pods per timestep by sum, except the two node-level series which are averaged across nodes; resampled onto a common 5s grid).
  2. **Static-threshold baseline comparator amended.** Component 3's original weakness-signal rule (error_rate > 5%, p99 > 3x baseline, recovery > 60s, pod_restarts > 0) needs per-timestep HTTP error/latency telemetry that does not exist here (item 1 above), and needs a whole-run recovery judgment that isn't a per-timestep quantity. The amended rule, applied uniformly and mechanically per timestep: score = count of (a) `pod_restarts_total` exceeding its own run's baseline-phase mean, and (b) any of the 6 non-restart features exceeding 3x its own run's baseline-phase mean (mirroring the original rule's "3x baseline" structure, applied to resource usage rather than latency since latency isn't observable per-timestep here). This is a NEW rule invented for this analysis, not equivalent to Component 3's original formula, and must be described as an adaptation in the manuscript, not presented as literally "the" Component 3 rule. It is also frequently degenerate: on 420 of 719 runs (58%) it registers zero violations for the entire run (constant score), most often for fault types that don't manifest as a 3x resource spike or a pod restart (e.g. moderate latency injection, packet loss) -- these runs are EXCLUDED from that scorer's AUC computation (a constant score makes AUC-ROC undefined, not literally 0.5, the same distinction already established for Component 4's degenerate-predictor finding) rather than silently reported as chance-level detection.
  3. **Training window is the run's authoritative baseline phase, not the sidecar's wider pre-buffer.** Component 1 amendment item 5 (above) already discloses that the sidecar's ~60s pre-baseline buffer (`window_start`) structurally overlaps roughly its first 40s with excluded warmup traffic, and that Component 1's 720 already-collected sidecars retain this uncorrected. Component 5 trains every detector only on `[phases.baseline.start, phases.fault.start)` from that run's own `run-N.json` (the authoritative, disclosed-clean 300s baseline phase), never on the sidecar's `window_start` buffer.
  4. **Bootstrap CI method and resample count registered explicitly.** The base Component 5 text above specifies "95% bootstrap CIs across runs" without a method or resample count. Registered now: percentile bootstrap (resampling the per-run median AUC), 10,000 resamples, fixed seed 42 -- the same count as Component 1 and Component 4's registered conventions, though the method itself (percentile, not BCa) is Component 5's own choice, disclosed rather than assumed to match either.
  5. **Compute platform: local (Apple Silicon CPU), not the dedicated EC2 instance the base text above names.** Total sidecar data is 85MB across all 720 runs; full evaluation (feature extraction + all 4 detectors + baseline, 719 runs) completes in under 2 minutes. This is an implementation detail, not a statistical-methodology decision, and does not affect any confirmatory analysis, but is disclosed here since the base text specifies otherwise.
- **Result (2026-08-18, first and only run against the real 720-run dataset):** Isolation Forest (median AUC 0.883, 95% CI [0.880, 0.889]) and the reconstruction autoencoder (median AUC 0.827, CI [0.825, 0.829]) both significantly beat the static-threshold baseline (paired Wilcoxon, Holm-corrected p < 0.001 for both). Deep SVDD (median AUC 0.805) does not significantly differ from the baseline (p = 0.570). EWMA (median AUC 0.582) is significantly WORSE than the baseline (p < 0.001). The static-threshold baseline itself has a genuine (non-degenerate) median AUC of 0.840 on the 299/719 runs where it registers any violation at all. Full per-run results: `analysis/results/component5-scoring.json`.
- Compute: detector training/scoring on a dedicated EC2 instance (no cluster interaction, post-collection).

## Metrics

- **Primary metric (Component 1): mean throughput (rps) during the fault window.** All confirmatory conclusions about tool differences rest on this metric alone.
- Secondary metrics (Component 1, reported with correction, labelled secondary): p99 latency during fault, error rate during fault, recovery time, pod restart count.
- **Primary metric (Component 3): discovery-curve AUC**, where the discovery curve is the cumulative count of unique weakness classes found after each of the 10 injections. Weakness classes are defined mechanically before any campaign runs: error rate > 5%, p99 > 3x scenario baseline median, recovery time > 60 s, pod restarts > 0; a weakness class instance is the (signal, target service) pair.
- Secondary metrics (Component 3): total unique weaknesses at K = 10, injections to first weakness.

## Confirmatory analyses

1. Component 1, per scenario: two-sided Mann-Whitney U comparing tools, n = 30 per arm.
2. Multiplicity: Holm-Bonferroni within each metric family (12 scenario-level tests per metric). The primary-metric family is the confirmatory family; secondary-metric families are reported as supporting evidence.
3. Effect sizes: Cliff's delta per scenario with 95% BCa bootstrap confidence intervals (10,000 resamples). Interpretation thresholds: |d| < 0.147 negligible, < 0.33 small, < 0.474 medium, otherwise large. No effect is described as meaningful in the text unless its CI excludes 0 after Holm-Bonferroni on the corresponding test.
4. Descriptives: medians and IQRs, not means, for all skewed metrics; percentage differences reported only alongside their CI.
5. Component 3: Kruskal-Wallis across the five arms on discovery-curve AUC (10 campaigns per arm); if p < 0.05, pairwise two-sided Mann-Whitney U with Holm correction. Cliff's delta with BCa CIs for pairwise effects.

## Power

- Component 1: at Holm-corrected worst-case alpha 0.05/12 = 0.0042, n = 30 per arm gives approximately 0.85-0.90 power for large effects (Cliff's |d| >= 0.474, roughly Cohen's d = 0.8 equivalent) under the Mann-Whitney U. Small effects are explicitly NOT powered; absence of significance for small effects will not be claimed as evidence of equivalence.
- Component 3: 10 campaigns per arm powers only large between-strategy differences; this is stated as a limitation.

## Exclusion and rerun rules

- A run is excluded and rerun only for infrastructure failure unrelated to the injected fault (node NotReady before fault start, load-generator job failing to schedule, Prometheus scrape gap > 30 s in the measurement window). Every exclusion is logged in `data/exclusions.log` with cause; the count is reported in the manuscript.
- Fault-induced application failure is DATA, never an exclusion.
- No interim analysis; no data-dependent stopping. Rep counts are fixed at 30/10/10 as above.

## What is exploratory

Anything not listed under Confirmatory analyses (per-category aggregations, cross-metric patterns, qualitative recovery-behavior observations) is reported as exploratory and labelled as such in the manuscript.
